# SAMS 시스템 구조 설계서 — 현재 버전

작성일: 2026-06-07  
문서 성격: 초기 시스템 구조 설계서를 기반으로, 2026년 5월 11일·6월 5일 회의와 현재까지의 mock 기반 개발 결과를 반영한 현재 버전 설계서

---

## 1. 시스템 정체성

### 1.1 시스템명

**SAMS — Spatial Assets Management System**

SAMS는 프로젝트 과정에서 생성되는 공간·비공간 산출물을 하나의 체계 안에서 등록, 탐색, 검토, 보완, 연결, 재활용하기 위한 사내 공간 자산 관리 시스템이다.

초기 설계서에서 SAMS는 “모든 프로젝트 산출물(공간+비공간)을 하나의 시스템에서 안전하게 보관하고, 누구나 검색으로 찾을 수 있게 하는 시스템”으로 정의되었다. 현재 버전에서는 이 정의를 한 단계 확장한다.

> SAMS는 파일을 보관하는 저장소가 아니라, 프로젝트 산출물을 공간 위치, 시간, 프로젝트 맥락, 데이터 유형, 상태, 관계로 읽을 수 있게 만드는 3D GIS 기반 공간 자산 탐색·관리 시스템이다.

### 1.2 시스템이 표현하고 싶은 것

SAMS가 표현하려는 것은 “파일 목록”이 아니다. SAMS가 표현하려는 것은 다음 네 가지다.

| 표현 대상 | 의미 | 화면에서의 표현 |
|---|---|---|
| 어디에 있는 데이터인가 | 산출물의 위치, 범위, coverage, boundary | Explorer의 3D GIS Asset Map, 2D map, coverage/boundary layer |
| 어떤 프로젝트의 데이터인가 | 프로젝트, 사이트, 발주처, PM, 기간, 기본 좌표계 | Project, Explorer filter, Context Panel |
| 어떤 상태의 데이터인가 | Draft, Published, Archived, preview 상태, 누락 필드 | badge, Draft queue, Metadata Completion |
| 무엇과 연결되는 데이터인가 | 원본/가공본, 문서 설명, 동시취득, prev/next 시계열 | 선택 Item 중심 relation overlay, timeline, Detail relation summary |

### 1.3 시스템의 핵심 화면 철학

Explorer는 SAMS의 중심이다. Explorer는 단순 검색 화면이 아니라 **3D GIS 기반 공간 자산 지도**로 발전해야 한다. 현재 안정적 탐색 경로로 2D map/list/context panel을 유지하지만, 장기적인 핵심 표현은 3D GIS이다.

3D GIS는 부가기능이 아니다. 현재 구현 성숙도가 Beta인 이유는 디자인, 클릭 UX, 렌더러, coverage/LOD 표현을 단계적으로 정교화하기 위해서다. 전체 mock workflow를 먼저 연결하면서도, 모든 설계 결정은 “Explorer가 결국 공간 자산을 3차원적으로 이해시키는 화면”이라는 방향을 기준으로 판단한다.

## 2. 사용자와 사용 목적

### 2.1 사용자 역할

| 역할 | 약칭 | 핵심 동기 | 시스템에서 원하는 결과 |
|---|---|---|---|
| 현장 담당자 | Acquirer | 취득한 데이터를 빠르게 등록하고 싶다 | 업로드 후 Draft로 안전하게 등록, 프로젝트에 연결 |
| 후처리 담당자 | Processor | 원본을 찾고 가공 결과를 연결하고 싶다 | derived_from, related, describes 관계를 남기고 가공본 등록 |
| PM | Manager | 프로젝트 산출물 현황을 한눈에 보고 싶다 | 프로젝트별 등록률, Draft, 누락 산출물, 공간 범위 확인 |
| 미래의 검색자 | Searcher | 맥락 없이 과거 데이터를 찾아야 한다 | 위치, 프로젝트명, 사람 이름, 파일명, 키워드, 관계로 탐색 |

현 단계에서는 사내 전용 시스템이므로 모든 사용자가 모든 기능에 접근할 수 있다. 역할은 권한 구분보다 화면 설계 우선순위를 정하기 위한 기준이다.

### 2.2 사용자 동선

#### Acquirer — 취득 데이터 등록

```text
Upload → 파일 선택 또는 mock file intake → 자동 분류 → Draft 등록
→ Explorer에서 새 Item 확인 → 프로젝트 연결 또는 metadata 보완
```

현장 담당자는 완벽한 메타데이터 입력보다 빠른 등록을 우선한다. SAMS는 데이터를 바로 Published로 만들기보다 Draft로 안전하게 수용하고, 이후 보완해야 할 항목을 시스템이 드러내야 한다.

#### Processor — 원본과 가공본 연결

```text
Explorer → 원본 검색 → Preview/Viewer 확인 → Upload 가공본 등록
→ derived_from 관계 설정 → Detail/Context Panel에서 관계 확인
```

후처리 담당자에게 중요한 것은 원본과 결과물의 계보가 끊기지 않는 것이다. SAMS는 `derived_from`, `describedby`, `related`, `prev`, `next` 같은 관계를 검색 이후의 부가 정보가 아니라 데이터의 품질과 신뢰도를 만드는 구조로 다룬다.

#### Manager — 프로젝트 단위 관리

```text
Project → 프로젝트 현황 확인 → Draft/누락 산출물 확인
→ 공간 범위 지도 확인 → Explorer로 유사 프로젝트 검색
```

PM에게 프로젝트는 폴더가 아니라 관리 단위다. 프로젝트는 등록률, Draft, 공간 coverage, 기간, 발주처, PM, 예상 산출물, 실제 산출물의 차이를 보여주는 대시보드여야 한다.

#### Searcher — 맥락 없는 검색

```text
Explorer → 키워드/공간/시간/프로젝트/유형 필터
→ 3D GIS 또는 2D map/list에서 위치와 유형 확인
→ Context Panel → Preview / Relation / Detail
```

미래의 검색자는 파일이 어디에 있는지, 누가 만들었는지, 어떤 프로젝트였는지 모를 수 있다. SAMS는 검색자가 데이터의 위치, 상태, 관계를 빠르게 이해하도록 Explorer를 가장 강한 진입점으로 설계한다.

## 3. 정보 모델

### 3.1 핵심 객체

| 객체 | 시스템 내부 의미 | 대표 필드/상태 | 화면 표현 |
|---|---|---|---|
| Project / Collection | 프로젝트 관리 단위 | id, title, site, client, period, manager, default_epsg, expected_deliverables | Project list, Project dashboard, Explorer project filter |
| Item | 하나의 공간/비공간 자산 단위 | geometry, bbox, datetime, data_category, status, project:name, project:site | Explorer marker/card, Context Panel, Detail |
| Asset | Item이 참조하는 실제 파일 또는 preview 파일 | original data, thumbnail, preview, overview, tileset, model, document | ViewerShell, Download, Preview |
| Relation | Item 간 관계 | derived_from, related, describedby, describes, prev, next | selected relation overlay, relation summary, timeline |
| Upload Task | 등록 전/등록 중 작업 단위 | file descriptors, classification, parse result, missing fields | Upload intake, Draft registration |
| Preview Contract | 파일을 열기 전 확인 가능한 미리보기 상태 | available, pending, missing, failed | Context Panel preview, ViewerShell |
| Spatial Layer | Item의 공간 표현 | point, bbox, footprint, coverage, boundary, flight_path | 2D map, 3D GIS, Spatial Summary |

### 3.2 STAC 기반 설계

SAMS는 STAC-like 구조를 내부 메타데이터 모델로 사용한다. STAC Item은 GeoJSON Feature로 읽을 수 있고, bbox, geometry, assets, links를 가진다. 이 구조는 SAMS가 Item을 지도 위에 놓고, 파일 asset을 연결하며, 관계 link를 통해 다른 Item으로 이동하게 만드는 데 적합하다.

SAMS에서 STAC은 단순 저장 포맷이 아니라 다음 세 가지 역할을 한다.

1. **검색 단위**: Explorer는 STAC Item FeatureCollection 형태의 결과를 받아 지도/목록/3D GIS에 동시에 표시한다.
2. **파일 연결 단위**: Item의 `assets`는 원본 파일, 썸네일, preview, overview, tileset, model, document를 연결한다.
3. **관계 표현 단위**: Item의 `links` 또는 relation record는 원본/가공본, 문서 설명, 시계열 관계를 표현한다.

### 3.3 데이터 유형

SAMS의 주요 `data_category`는 다음과 같다.

| data_category | 의미 | 기본 공간 표현 | Preview/Viewer 방향 |
|---|---|---|---|
| pointcloud | LiDAR/LAS/LAZ 등 포인트 클라우드 | point, bbox, coverage footprint, 3D volume marker | thumbnail → point cloud viewer |
| 3d_model | OBJ/GLB/PLY/BIM/photogrammetry model | bbox, boundary, footprint, 3D marker | screenshot → model viewer |
| 3d_tiles | tileset.json 기반 3D Tiles | tileset boundary, bbox, LOD marker | tileset placeholder → 3D Tiles renderer |
| orthoimage | 정사영상/GeoTIFF/orthomosaic | footprint polygon, coverage | image-style preview → tiled/GeoTIFF viewer |
| image | 원본 이미지/드론 사진 묶음 | point, coverage polygon | image preview / slideshow |
| panorama | 360 파노라마 | point, field-of-view, dome marker | panorama viewer |
| video | 영상/동선 기록 | point, route, time marker | poster/native video viewer |
| document | 보고서/허가서/계약서/메모 | linked location or project fallback | document preview/PDF viewer |

### 3.4 상태 모델

| 상태 | 의미 | 시스템이 표현하는 방식 |
|---|---|---|
| Draft | 등록은 되었지만 메타데이터, 위치, preview, 관계, 프로젝트 연결 중 일부가 보완 필요 | 노란 badge, Draft reason, missing fields, 보완 CTA |
| Published | 검색과 재사용에 필요한 최소 품질 기준을 만족 | 일반 검색 결과, project dashboard 반영 |
| Archived | 과거 데이터로 보존되며 기본 작업 대상은 아님 | muted 표시, archive filter |
| Unknown | 상태 정보가 없거나 규칙 밖의 값 | neutral 표시, 품질 점검 대상 |

Draft는 실패 상태가 아니다. Draft는 SAMS가 데이터를 잃지 않고 먼저 수용한 뒤, 사람이 보완해야 할 항목을 명확히 알려주는 작업 상태다.

### 3.5 관계 모델

| rel | 의미 | 예시 | 표현 위치 |
|---|---|---|---|
| derived_from | 가공본이 원본에서 파생됨 | 3D model derived_from drone photos | Relation overlay, Detail |
| related | 동시취득 또는 느슨한 관련 | scan related to site video | Relation summary |
| describedby | 문서가 Item을 설명함 | pointcloud describedby report | Context Panel, Detail |
| describes | Item이 문서를 설명 대상으로 가짐 | report describes model | Context Panel, Detail |
| prev | 이전 시점 | 2022 scan → 2024 scan | Timeline |
| next | 다음 시점 | 2024 scan → 2026 plan | Timeline |

Explorer에서는 모든 관계를 항상 펼치지 않는다. 관계는 선택한 Item을 중심으로 드러난다. 이렇게 해야 공간, 프로젝트, 상태, 유형을 먼저 읽고, 그 다음 관계를 이해할 수 있다.

## 4. 화면 구조 — 현재 버전

### 4.1 전체 내비게이션

```text
┌───────────────────────────────────────────────────────────────┐
│ SAMS                                                         │
│ [Explorer] [Project] [Upload] [User/Settings]                 │
└───────────────────────────────────────────────────────────────┘

Core Screens:
- Explorer: 공간 자산 탐색의 중심
- Project: 프로젝트 단위 현황과 관리
- Upload: 데이터 수용과 Draft 생성

Contextual Surfaces:
- Context Panel: 선택 Item의 판단 정보
- ViewerShell: 가벼운 preview / viewer 진입
- Metadata Completion: Draft 보완
- Detail: Item의 전체 정보와 관계/시계열
```

초기 설계서가 Explorer, Project, Upload, 사용자 메뉴를 상단 페이지 구조로 제안했다면, 현재 버전은 여기에 Context Panel, ViewerShell, Metadata Completion을 명시적인 화면 표면으로 추가한다. 이들은 별도의 주 메뉴가 아니라 사용자가 Item을 선택한 뒤 자연스럽게 열리는 작업 표면이다.

## 5. Explorer — 3D GIS 기반 공간 자산 탐색

### 5.1 Explorer의 역할

Explorer는 SAMS의 중심 화면이다. Explorer는 “검색창 + 목록”이 아니라 공간 자산을 이해하는 지도다. 사용자는 Explorer에서 데이터의 위치, 범위, 유형, 상태, 프로젝트, 관계를 동시에 읽는다.

### 5.2 Explorer의 현재 구조

```text
┌────────────────────────────────────────────────────────────────────┐
│ Explorer                                                           │
├──────────────┬──────────────────────────────────────┬──────────────┤
│ Search/Filter │  Asset Map Area                      │ Context Panel │
│              │  - 3D GIS Asset Map                  │              │
│ keyword      │  - 2D Map/List stable path           │ Preview      │
│ status       │  - coverage/boundary layer 예정       │ Identity     │
│ category     │  - selected relation overlay          │ Project      │
│ project      │                                      │ Metadata     │
│ time         │  Result List와 같은 visibleItems 사용 │ Spatial      │
│ spatial      │                                      │ Relation     │
└──────────────┴──────────────────────────────────────┴──────────────┘
```

### 5.3 Explorer가 반드시 표현해야 하는 것

| 표현 | 이유 | 현재/향후 화면 방식 |
|---|---|---|
| 위치 | 산출물은 위치를 통해 발견되고 비교된다 | marker, 3D GIS object, coverage, bbox |
| 범위 | 드론/정사영상/3D 모델은 점이 아니라 영역을 가진다 | coverage polygon, footprint, boundary |
| 높이/고도 | 지하/지상/옥상/공중 취득 데이터는 같은 평면에 있지 않다 | z/elevation policy, 3D GIS vertical expression |
| 유형 | 데이터별 의미와 viewer가 다르다 | category icon, marker shape, badge |
| 상태 | Draft와 preview 실패를 빠르게 찾는다 | status chips, badges, warning panel |
| 프로젝트 | PM은 프로젝트 단위로 데이터를 판단한다 | project filter, project badge, Project page |
| 관계 | 데이터는 원본/가공/문서/시계열로 연결된다 | selected 1-depth relation overlay |

### 5.4 3D GIS의 지위

3D GIS는 Explorer의 핵심 목표 화면이다. 현재 구현은 다음 세 단계를 거쳤다.

1. **Pseudo 3D Beta** — 같은 visibleItems, selectedItem, Context Panel, relation overlay 의미가 3D-ish 화면에서도 유지되는지 확인했다.
2. **True 3D Spike** — Three.js로 perspective camera, orbit, zoom, ray picking, category geometry를 검증했다.
3. **Map-grounded 3D Spike** — MapLibre 배경지도 위에 Three.js category object를 올려 georeferencing 방향을 검증했다.

현재 3D GIS는 Beta maturity이다. 이 말은 중요도가 낮다는 뜻이 아니다. 3D GIS가 SAMS Explorer의 핵심 목표이기 때문에, 실제 데이터 구조와 전체 업무 흐름을 mock으로 연결하면서 렌더링, 클릭성, coverage, LOD, label, relation 표현을 단계적으로 고도화한다.

### 5.5 Explorer의 관계 표현 원칙

Explorer는 global Relationship Graph를 기본 화면으로 삼지 않는다. 관계는 선택 Item 중심으로 드러난다.

```text
사용자가 Item 선택
→ Context Panel에 relation summary 표시
→ 사용자가 “지도에서 관계 보기” 클릭
→ 선택 Item의 1-depth relation만 지도/3D GIS에 표시
→ 현재 검색 결과 밖 relation target은 warning으로 표시
```

이 원칙은 관계를 숨기기 위한 것이 아니라, 관계를 공간 탐색 흐름 안에서 읽히게 하기 위한 것이다.

## 6. Context Panel — 선택 Item의 판단 표면

### 6.1 역할

Context Panel은 사용자가 Explorer에서 Item을 클릭했을 때 “이 데이터를 열어볼 가치가 있는지”, “보완해야 할 것이 무엇인지”, “무엇과 연결되어 있는지”를 즉시 판단하게 하는 표면이다.

### 6.2 정보 구조

| 섹션 | 보여주는 것 | 이유 |
|---|---|---|
| Preview summary | available/pending/missing/failed, thumbnail, failure reason | 파일을 열기 전 빠른 판단 |
| Identity | 사람이 읽는 제목, 원본 파일명, Item ID, 파일 크기 | 자동 ID와 사람이 이해하는 이름을 분리 |
| Project/Status | project, site, collection, status, preview status | 프로젝트 맥락과 품질 상태 확인 |
| Metadata quality | draftReason, missingRequiredFields, metadataGaps | Draft 보완 대상 명확화 |
| Spatial summary | geometry, bbox, fallback, coverage/boundary 예정 | 지도에 표시된 위치의 근거 설명 |
| Relation summary | rel별 count, missing target, relation CTA | 선택 Item 주변 관계 확인 |
| Action footer | Detail, ViewerShell, Metadata Completion, Project 연결 | 다음 행동으로 이동 |

Context Panel은 Detail 전체를 대체하지 않는다. Context Panel은 Explorer 안에서 빠르게 판단하게 하고, 더 깊은 확인이 필요한 경우 Detail, ViewerShell, Metadata Completion, Project로 이어진다.

## 7. ViewerShell과 Preview 전략

### 7.1 Preview의 목적

Preview는 원본 파일을 다운로드하거나 heavy viewer를 열기 전에 데이터의 상태와 내용을 빠르게 판단하게 한다. Preview는 “보여줄 수 있는 파일”만 처리하는 기능이 아니라, “왜 아직 볼 수 없는지”까지 표현하는 상태 계약이다.

### 7.2 Preview 상태

| previewStatus | 의미 | 화면 표현 |
|---|---|---|
| available | preview asset 또는 lightweight preview가 있음 | preview card, ViewerShell action |
| pending | 변환/생성/검수 대기 중 | preparation shell, 상태 badge |
| missing | preview asset 없음 또는 생성 미시작 | conversion-needed shell |
| failed | preview 생성 실패 | failure shell, failureReason |

### 7.3 ViewerShell 전략

ViewerShell은 production heavy viewer가 아니다. ViewerShell은 다음을 검증하는 lightweight surface다.

- category별 viewer 진입 UX
- available/pending/missing/failed 상태 메시지
- image/ortho preview source loading/fallback
- failure reason과 diagnostics 표시
- Detail handoff

Production viewer는 data_category별로 단계적으로 붙인다.

| data_category | 현재 ViewerShell | production 후보 |
|---|---|---|
| image / orthoimage | browser-loadable preview image, zoom/reset, diagnostics | tiled image/GeoTIFF viewer |
| document | placeholder / conversion-needed | PDF.js 또는 server-rendered pages |
| video | poster/placeholder | native video player + signed delivery |
| panorama | placeholder/failure | panorama renderer |
| 3d_model | screenshot/placeholder | model viewer / GLB pipeline |
| pointcloud | thumbnail/conversion-needed | Potree 등 point cloud viewer |
| 3d_tiles | tileset placeholder | Cesium 또는 3D Tiles renderer |

## 8. Project — 프로젝트 단위 현황과 관리

### 8.1 Project의 역할

Project는 Collection 단위의 관리 화면이다. Explorer가 “어디에 어떤 데이터가 있는가”를 보여준다면, Project는 “이 프로젝트가 어떤 상태인가”를 보여준다.

PM은 Project 화면에서 다음을 알고 싶다.

- 예상 산출물 대비 실제 등록 수량
- Draft 또는 미보완 산출물
- project site, period, client, PM, default EPSG
- 공간적으로 어떤 영역에 어떤 산출물이 있는지
- 미할당 Item을 프로젝트에 연결해야 하는지

### 8.2 Project 화면 구조

```text
┌────────────────────────────────────────────────────────────┐
│ Project                                                    │
├──────────────┬─────────────────────────────────────────────┤
│ Project List │ Project Header                              │
│              │ - title, site, client, PM, period, EPSG     │
│ active       │ - asset count, Draft count, completeness    │
│ archived     │                                             │
│ unassigned   │ Tabs                                        │
│              │ - 현황                                      │
│              │ - 공간                                      │
│              │ - Draft                                     │
│              │ - 전체 Item                                 │
│              │ - Timeline/Lineage                          │
└──────────────┴─────────────────────────────────────────────┘
```

### 8.3 Project가 표현해야 하는 핵심

| 표현 | 이유 | 구현 방향 |
|---|---|---|
| 등록 현황 | PM은 누락 산출물을 수량으로 파악한다 | expected_deliverables vs registered count |
| Draft 목록 | 보완 작업을 프로젝트 단위로 관리한다 | Draft tab, metadata gap chips |
| 공간 현황 | 프로젝트 범위와 산출물 coverage를 확인한다 | project-filtered map / 3D GIS extent |
| Asset 연결 | 하나의 asset이 여러 프로젝트에 재사용될 수 있다 | project assignment UI, multi-project link |
| Unassigned 정리 | upload-* 임시 프로젝트/미할당 상태를 관리한다 | Unassigned Inbox, assignment flow |

## 9. Upload — 데이터를 안전하게 수용하는 입구

### 9.1 Upload의 역할

Upload는 완성된 데이터만 받는 문이 아니다. Upload는 불완전한 데이터도 잃지 않고 수용한 뒤, 자동 분류와 Draft 보완 흐름으로 연결하는 입구다.

### 9.2 단건 업로드와 벌크 업로드

| 기준 | 단건 업로드 | 벌크 업로드 |
|---|---|---|
| 사용 상황 | 특정 파일 1~2개 정밀 등록 | 프로젝트 산출물 다수 등록 |
| 핵심 가치 | 정밀도 — 모든 메타데이터 직접 확인 | 효율성 — 공통값 일괄 입력 |
| 메타데이터 편집 | 전체 필드 확인/수정 | 테이블 기반 공통/개별 편집 |
| 관계 설정 | 시각적 관계 설정 | manifest/excel 기반 관계 입력 |
| 주 사용자 | Processor | Acquirer, Manager |

### 9.3 Mock-first Upload 전략

실데이터 업로드는 mock workflow가 온전해진 뒤 진행한다. 다음 단계에서 Upload는 실제 파일 대신 mock file descriptor를 사용한다.

```text
mock file 선택
→ 자동 분류 결과 표시
→ preview/spatial/metadata 상태 예측
→ Draft로 등록
→ Explorer에서 새 Item 확인
→ Metadata 보완 / Project 연결
```

이 방식은 무거운 파일 최적화에 매몰되기 전에 전체 제품 흐름을 검증하기 위한 설계 선택이다.

### 9.4 Mock Upload 데이터 예시

| 파일명 | 예상 분류 | 예상 상태 | 표현하고 싶은 것 |
|---|---|---|---|
| basement_lidar_scan.laz | pointcloud | Draft, CRS 확인 필요 | LiDAR 등록과 좌표계 누락 |
| lobby_bim_model.glb | 3d_model | Preview pending | 모델 preview 변환 대기 |
| rooftop_ortho.tif | orthoimage | TIFF unsupported preview | GeoTIFF/정사영상 preview 전략 |
| drone_photos_facade.zip | image set | coverage 필요 | 묶음 이미지와 coverage |
| drone_flight_path.geojson | flight_path/vector | spatial available | 비행 궤도 line |
| tileset.json | 3d_tiles | tileset boundary 필요 | 3D Tiles 등록 |
| site_walkthrough.mp4 | video | poster pending | video preview/pipeline |
| permit_memo.pdf | document | metadata manual required | 문헌정보와 fallback spatial context |

## 10. Metadata Completion — Draft를 작업 가능한 상태로 만들기

### 10.1 역할

Metadata Completion은 Draft Item을 Published 후보로 만드는 작업 화면이다. 사용자는 누락된 필드가 무엇인지 알고, 입력하고, 저장 후 품질 상태가 어떻게 바뀌는지 확인한다.

### 10.2 화면 구조

```text
Metadata Completion
├ Item Summary
│  ├ title / original filename / category / project
│  └ draft reason / preview status / spatial status
├ Required Fields
│  ├ project:name
│  ├ project:site
│  ├ datetime
│  ├ proj:epsg
│  └ data_category
├ Type-specific Fields
│  ├ pc:count / 3dmodel:format / ortho:gsd ...
├ Quality Gate
│  ├ Published 가능
│  └ 아직 보완 필요
└ Actions
   ├ 저장
   ├ Explorer로 돌아가기
   └ Project 연결
```

### 10.3 Published 전환의 의미

Published는 “완벽함”을 의미하지 않는다. Published는 검색자가 재사용하기 위해 필요한 최소 품질 기준을 통과했다는 뜻이다. Preview failure나 일부 optional field는 남을 수 있지만, 그 사유가 명확히 기록되어야 한다.

## 11. Detail — 깊은 확인과 관계/시계열 탐색

### 11.1 역할

Detail은 선택 Item의 전체 정보를 확인하는 화면이다. Explorer의 Context Panel이 빠른 판단 표면이라면, Detail은 문서화된 전체 기록이다.

### 11.2 Detail이 표현하는 것

- 원본/preview/download asset
- 전체 metadata
- 자동 추출 metadata와 수동 입력 metadata의 구분
- 관계 mini graph 또는 relation tab
- prev/next timeline
- 파일 교체/수정 이력
- project assignment history

### 11.3 관계 그래프의 위치

관계 그래프는 Explorer의 메인 화면을 대체하지 않는다. 관계 그래프는 Detail에서 선택 Item을 중심으로 깊게 탐색하는 보조 구조로 위치한다. Explorer에서는 지도/3D GIS 위 selected 1-depth overlay로 관계를 빠르게 확인하고, Detail에서는 더 깊은 관계와 시계열을 본다.

## 12. 공간 표현 정책

### 12.1 위치 표현 우선순위

Item을 지도/3D GIS에 놓는 위치는 다음 우선순위를 따른다.

1. geometry center
2. bbox center
3. project/site fallback location
4. no spatial marker 상태 표시

문서, 계약서, 보고서처럼 직접 좌표가 없는 데이터도 시스템에서 사라지지 않는다. 해당 문서가 설명하는 프로젝트 또는 연결된 공간 자산의 맥락을 통해 fallback 위치로 나타난다.

### 12.2 Coverage / Boundary / Flight Path

향후 SAMS의 공간 표현은 점 marker에만 머물지 않는다.

| 공간 표현 | 적용 대상 | 의미 |
|---|---|---|
| point | 사진, 문서 fallback, 단일 취득 지점 | 기준 위치 |
| bbox | 3D model, pointcloud, 3D Tiles | 빠른 범위와 fit bounds |
| footprint | orthoimage, 3D model | 실제 지면 투영 범위 |
| coverage polygon | drone photo set, pointcloud set | 취득 범위 |
| flight path line | drone flight, video route | 취득 경로 |
| 3D boundary / volume | model, tiles, pointcloud | 높이와 부피/범위 |

### 12.3 3D GIS에서의 표현

3D GIS는 다음을 표현해야 한다.

- 같은 위치에 여러 asset이 있을 때의 수직/층위 차이
- 지하/지상/옥상/공중 취득 데이터의 Z 의미
- pointcloud, 3D model, 3D tiles의 공간 volume
- image/ortho/video/document의 가벼운 marker/plate/card 표현
- 선택 Item 중심 관계선과 related asset highlight
- 시계열 prev/next의 공간적 변화

현재 3D object는 production viewer가 아니라 asset marker다. 향후 coverage, boundary, LOD가 붙으면 marker와 실제 데이터 범위가 구분되어야 한다.

## 16. 설계 선택과 이유

### 16.1 Explorer를 3D GIS 중심으로 두는 이유

SAMS의 데이터는 대부분 위치와 범위를 가진다. 같은 장소에서 pointcloud, 3D model, 3D tiles, orthoimage, image, panorama, video, document가 함께 존재한다. 2D 지도만으로는 지하/지상/옥상/공중 취득 데이터와 시간에 따른 변화, 관계의 방향성을 충분히 표현하기 어렵다.

3D GIS는 이 복잡도를 “공간 속에서 읽는 방식”으로 바꾼다. 사용자는 3D GIS에서 산출물의 높이, 범위, 관계, 시간 흐름을 직관적으로 파악할 수 있다.

### 16.2 2D map/list를 유지하는 이유

2D map/list는 현재 가장 안정적인 검색과 선택 경로다. 3D GIS가 핵심 방향이더라도, 사용자는 목록과 필터로 빠르게 결과를 좁히고, 2D 지도에서 위치를 확인할 수 있어야 한다. 따라서 2D map/list는 fallback이 아니라 3D GIS를 보완하는 안정 탐색 경로다.

### 16.3 Mock-first로 가는 이유

실데이터는 무겁고 다양하다. 지금 실데이터를 바로 넣으면 전체 시스템 흐름보다 개별 파일 변환, 포맷 오류, preview 최적화에 매몰될 수 있다. Mock-first는 다음을 먼저 고정한다.

- 어떤 화면에서 사용자가 무엇을 클릭하는가
- Draft가 어떻게 보이고 보완되는가
- Project 연결이 어떻게 흐르는가
- 관계와 시계열이 어떻게 만들어지는가
- coverage/boundary가 어떤 의미로 표시되는가

이 흐름이 확인된 뒤 작은 실데이터 pilot을 시작한다.

### 16.4 선택 Item 중심 관계를 사용하는 이유

관계는 중요하지만, 모든 관계를 한꺼번에 펼치면 Explorer가 공간 탐색 화면이 아니라 복잡한 그래프 보드가 된다. SAMS는 관계를 숨기지 않는다. 대신 사용자가 특정 Item을 선택했을 때 그 Item을 이해하는 데 필요한 관계를 집중적으로 보여준다.

## 17. 현재 버전의 결과물 정의

현재 버전의 SAMS 시스템 구조 설계서는 다음 결과를 목표로 한다.

1. **Explorer 중심성 확정**  
   Explorer는 검색 화면이 아니라 SAMS의 공간 자산 해석 중심이다.

2. **3D GIS 핵심 방향 확정**  
   3D GIS는 선택적 부가 기능이 아니라 Explorer의 장기 핵심 화면이다. 현재는 Beta maturity로 유지하며, 전체 mock workflow와 함께 고도화한다.

3. **Mock-first 개발 원칙 확정**  
   실데이터 pilot 전까지 mock으로 Upload, Draft, Explorer, Project, Metadata, Relation, Timeline 흐름을 끝까지 연결한다.

4. **Context Panel의 역할 확정**  
   사용자는 Item을 클릭하면 즉시 preview, 상태, 누락, 공간 근거, 관계 요약을 판단한다.

5. **Project와 Upload의 위치 재정의**  
   Project는 PM의 관리 대시보드이고, Upload는 데이터를 Draft로 안전하게 수용하는 입구다.

6. **Preview/Viewer 분리**  
   Preview는 상태 계약이며, production viewer는 category별로 단계적으로 붙인다.

7. **관계/시계열 구조 확정**  
   Explorer는 selected 1-depth relation, Detail은 더 깊은 관계/시계열 탐색, Project는 프로젝트 단위 관계/lineage를 담당한다.
